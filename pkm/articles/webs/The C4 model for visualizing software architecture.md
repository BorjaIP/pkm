# TL;DR

The **C4 model** documents software architecture with hierarchical abstractions and diagrams at four zoom levels: system, container, component, code.

# What it covers

An approach to architecture diagramming defined as three parts: hierarchical **abstractions** (software system, container, component, code), hierarchical **diagrams** (system context, containers, components, code) and **supporting diagrams** (system landscape, dynamic, deployment). It is notation- and tooling-independent. The site also links a book, talks, training and FAQs.

# Key takeaways

1. **Zoom in four levels**: system context, then containers, components and finally code.
2. **Use supporting diagrams** for the landscape of systems, runtime behaviour (dynamic) and deployment.
3. **Stay notation independent**: boxes and lines are enough if each element is labelled and explained.
4. **Stay tool independent**: use any drawing or diagram-as-code tool.
5. **Review diagrams** with a checklist (linked from the site).

# When to use

1. When **drawing or reviewing architecture diagrams** for a system.
2. When you need a shared vocabulary for **abstraction levels** in design docs.
3. When explaining a system to different audiences at different zoom levels.
